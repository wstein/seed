= Architecture Decisions
:page-layout: default

Capture the architectural choices that deserve durable context.

== Decision Log

The decisions below shape how Seed ports ANTLR4 to the BEAM. Each is
recorded as a lightweight ADR: context, the decision, and its
consequences.

[#adr-001]
=== ADR-001: Reuse the ANTLR tool; port only the runtime

*Status:* Accepted

*Context:* ANTLR4 separates the grammar *tool* (the code generator) from
the per-language *runtime*. The tool runs at build time and its output is
language-neutral. Re-implementing the tool in Elixir would reproduce the
ATN construction and adaptive LL(*) analysis — the most intricate part of
the project — with no user-facing benefit.

*Decision:* Seed implements a BEAM *runtime* and an Elixir
code-generation target only. The grammar tool (canonical ANTLR4, or
antlr-ng) is reused unchanged.

*Consequences:* Dramatically smaller scope. Seed tracks the tool's output
format rather than its internals. The choice of which tool authors the
Elixir target is deferred to the code-generation milestone; the runtime is
tool-agnostic because it consumes serialized output (see <<adr-002>>).

*Amendment (see <<adr-007>>):* "with no user-facing benefit" was true while
the runtime did not exist. Now that the runtime is mature and validated, a
self-hosting Elixir tool would remove the external Java/TypeScript build
dependency. ADR-007 plans that tool as a separate, opt-in milestone; it does
not void this decision (the tool/runtime split stands — Seed simply provides
both), and the reused tool remains fully supported.

[#adr-002]
=== ADR-002: The serialized ATN is the contract

*Status:* Accepted

*Context:* The ANTLR tool serializes a grammar's ATN to a flat array of
integers. Every runtime deserializes and simulates that array. The format
is stable and identical across the canonical tool and antlr-ng.

*Decision:* Seed treats the serialized ATN integer stream as its contract
with the tool. It deserializes that stream and never reconstructs an ATN
from a grammar.

*Consequences:* The existing ANTLR grammar corpus becomes a ready-made
conformance oracle — any grammar the tool can serialize, Seed can attempt
to run, and decisions can be diffed against the reference runtime. Seed
must track the serialization version the tool emits. That version is **4**
across ANTLR4, antlr-ng, and the in-development ANTLR5, so the deserializer
spans all three; a grammar is loaded from the tool's `.interp` file (see
Seed.Interp), which bundles this stream with the token, rule, channel, and
mode names.

[#adr-003]
=== ADR-003: Idiomatic at the edges, faithful at the core

*Status:* Accepted

*Context:* ANTLR's reference runtime is aggressively object-oriented:
inheritance, listener/visitor classes, exceptions for control flow, and
mutable simulator state. A literal transliteration would feel foreign on
the BEAM; an unconstrained re-imagining of the prediction engine would
have no oracle to validate against.

*Decision:* The public API is idiomatic Elixir — structs, behaviours,
pattern matching, and `{:ok, result} | {:error, reason}` results. The
prediction-engine internals (the ATN simulators, prediction context, and
configuration-set merging) remain a faithful transliteration of the
reference runtime.

*Consequences:* "Idiomatic" stops at the facade. Creativity is forbidden
in the prediction core, where it would produce undetectable parsing bugs.
Code generation that uses Elixir macros must still emit inspectable source
so the generated parsers remain debuggable.

[#adr-004]
=== ADR-004: Pure functions, not processes, for parsing

*Status:* Accepted

*Context:* A parse is a deterministic transformation of tokens into a tree.
Wrapping a parser in a `GenServer` would add a mailbox bottleneck and
hidden state without benefit.

*Decision:* Lexers and parsers are plain modules and functions with no
process identity. Concurrency and per-parse isolation are the caller's
concern, achieved by running parses inside the caller's own processes.

*Consequences:* Parsing stays referentially transparent and trivially
testable. The BEAM's strength — many isolated concurrent parses — is
available to callers without Seed imposing a process model.

[#adr-005]
=== ADR-005: ETS for the adaptive DFA cache; persistent_term for the static ATN

*Status:* Accepted

*Context:* Adaptive LL(*) performance depends on a mutable DFA cache that
grows as the parser observes new lookahead, while the deserialized ATN
itself is large and immutable. The BEAM has no shared mutable maps by
default; naive choices either lose cross-parse memoization or serialize
all predictions through one process.

*Decision:* Store the static, immutable ATN in `:persistent_term` for
zero-copy concurrent reads. Hold the adaptive DFA cache in `ETS`, bounded
and evictable to prevent unbounded growth under adversarial input.

*Consequences:* Cross-parse memoization is preserved without a process
bottleneck. The cache bound is a deliberate denial-of-service mitigation.
`:persistent_term` is used only for the static ATN — never for
per-parse data — because writes to it trigger a global GC.

*Status of implementation:* `Seed.DFACache` (a supervised, bounded ETS
table owned by `Seed.Application`, keyed per grammar via the ATN's
`cache_key`) memoizes both the lexer and parser simulators' start-state
closures and edge reaches. It degrades to recomputation when the table is
absent, so it never changes results.

The static ATN is held as a plain immutable term, **not** in
`:persistent_term`. A concurrent-parse benchmark (`bench/parse_bench.exs`,
on the JSON grammar — a ~35 KiB ATN) found no throughput gain from
`:persistent_term`: the ATN is copied into a process once and amortized
over the parses it runs, so by-value parsing is as fast as (or faster than)
shared reads in the realistic long-lived-worker case, and only marginally
faster one-parse-per-process. `:persistent_term` is therefore deferred
until a substantially larger grammar or a one-parse-per-process workload
measurably justifies it — consistent with the measure-first stance of
ADR-006.

[#adr-006]
=== ADR-006: Defer native acceleration (NIF) until measured

*Status:* Accepted

*Context:* The BEAM is slower than Go or the JVM on the tight,
integer-heavy loops of ATN simulation. A Rust NIF for the hot path would
recover speed but would mean Seed is not truly a BEAM port, and it would
break single-command installation and deterministic builds.

*Decision:* Seed v1 is pure Elixir. A native NIF for the prediction core
is an explicit, opt-in escape hatch reserved for v2, gated on real
benchmarks rather than speculation.

*Consequences:* Installation stays `mix`-simple. Single-parse throughput
is a documented tradeoff; concurrent-parse isolation is the compensating
strength.

[#adr-007]
=== ADR-007: A self-hosting Elixir grammar tool (`.g4` → ATN)

*Status:* Proposed

*Context:* <<adr-001>> deferred the grammar tool — `.g4` parsing, semantic
analysis, and ATN construction — because reproducing it had "no user-facing
benefit" while no runtime existed. That premise has changed. The runtime is
now mature and oracle-validated, which makes a self-hosting tool both
worthwhile and unusually tractable:

* *Worthwhile* — it removes the external Java/antlr-ng dependency from the
  build, giving a pure-BEAM grammar-to-parser pipeline (`mix`-only, no JVM),
  which matters for reproducible builds and BEAM-native deployment.
* *Tractable* — the tool's output is exactly the `%Seed.ATN{}` the runtime
  already consumes, so construction has a *precise, executable target*; and
  the canonical tool emits a serialized ATN for any grammar, so every step
  has a *differential oracle* (`Seed.ATNDeserializer` turns the reference's
  `.interp` into a `%Seed.ATN{}` to diff against — no ATN *serializer* is
  needed). The `.g4` front end bootstraps on Seed's own runtime using the
  ANTLR-grammar ATN as a fixture.

*Decision:* Plan — do not yet build — a self-hosting tool as a distinct,
opt-in milestone, validated phase by phase against the reference ATN. It
keeps the <<adr-002>> serialized-ATN structure as its internal target so the
runtime is unaffected. ADR-001's tool/runtime split is preserved; Seed gains
a *second* tool option alongside the reused one, not a replacement.

*Phased plan (each diffed against the reference `.interp` for the existing
fixtures — Hello → Expr → Ctx → Cover → JSON):*

[cols="1,5",options="header"]
|===
| Phase | Work

| 0. Bootstrap _(spike done)_ | Parse `.g4` with Seed's own runtime, driven by a grammar-for-grammars ATN from the reference tool. Demonstrated by `Seed.G4BootstrapTest`: a `G4.g4` covering a subset of ANTLR syntax parses Seed's own fixtures (Hello, Expr, Hidden, Ctx), and the result is queryable with `Seed.XPath`. Constructs beyond the subset (semantic predicates, embedded actions, `..` ranges) and the official adaptor-driven lexer are later iterations.
| 1. Grammar model | Build the AST and symbol model from the `.g4` parse tree: rules, tokens, literals, fragments, channels, modes; resolve references; assign token types.
| 2. Lexer ATN | Construct the lexer ATN (rules, sets/ranges, EBNF blocks, lexer commands) and diff the `%Seed.ATN{}` against the reference `*Lexer.interp`.
| 3. Parser ATN | Construct the parser ATN (alternatives, EBNF block/loop states, decisions, rule-stop and follow wiring) and diff against the reference `.interp`.
| 4. Left recursion | Apply the precedence-climbing transform (the hardest phase, isolated) and diff.
| 5. Analysis & emit | Grammar diagnostics (collisions, unreachable rules), vocabulary, and `.interp`/`Seed.Grammar` emission; optionally an ATN *serializer* for `.interp` round-tripping.
|===

*Consequences:* Roughly doubles the codebase; the oracle de-risks
correctness, not effort. It does *not* unblock the runtime's
embedded-action/predicate execution — that is a runtime concern
(<<adr-003>>, and the predicate callbacks added for grammars that need
disambiguation) and is orthogonal to building the tool. Grammar analysis is
in scope only as needed to construct a correct ATN; replicating every
reference warning is not a goal. Until the milestone ships, the reused
ANTLR/antlr-ng tool remains the supported path
(xref:manual:feature-parity.adoc[Feature Parity And Roadmap]).
